# game_analyze 设计提案

状态：提案，尚未实现。日期：2026-10-13。

目标：在当前 MCP 上增加按需调用的只读分析工具，把组合枚举、计分、补牌概率和构筑比较交给程序，把战略取舍与动作执行留给调用方模型。

本文依据当前工具层、桥接源码和 `balatro-ai` 的分析代码独立设计。工作区已有未提交的 Lua 影子计分实现；本文只描述与它的接口边界，不修改或假定其已经通过验证。下文新增文件、字段、能力和性能数字均是实施建议，不是当前已提供的功能。

## 1. 产品边界

一次分析回答三个问题：现在有哪些值得比较的选择、这些选择有哪些可计算的差异、计算依赖哪些假设。结果必须足够短，能直接辅助下一次决策。

- `game_observe`：玩家现在看到了什么。
- `game_analyze`：根据这些公开信息，候选选择会有什么可计算的结果。
- `game_action`：执行一个选择，由原游戏最终检查合法性并结算。

分析不执行候选、不排队动作、不启动或继续游戏、不替模型维护长期计划。它也不调用另一个模型。第一阶段提供当前手牌的出牌与排列分析；之后加入有限补牌和商店构筑分析。完整回合搜索、未来商店预测和整局胜率不在这版范围内。

分析按需调用，不默认把大段分析塞进每次观察或动作返回。遇到明显的收款、过渡阶段，调用方可以直接操作；遇到难算的出牌、排列或购买，再请求分析。

## 2. MCP 接口

目标接口如下，未知参数一律拒绝：

```ts
type AnalyzeInput = {
  revision: string;
  focus?: 'auto' | 'play' | 'draw' | 'build'; // 默认 auto
  limit?: number;                          // 默认 5，整数 1..8
  plays?: number[][];                      // 可选：只比较指定出牌
};
```

`plays` 最多 8 组，每组 1–5 个不重复的零基下标；范围还受当前选择上限约束。只允许在解析后的 `focus=play` 时使用。重复组按集合去重，保留第一次出现的位置。指定比较时返回每组结果，不按 `limit` 丢弃其中任何一组；`limit` 只限制自动生成的候选。它只指定选择哪些牌，**数组顺序不表示出牌顺序**；出牌顺序取当前手牌排列。

调用方不能传入伪造状态、修改 Joker 数值、指定隐藏牌、指定游戏种子或控制内部采样种子。预算和采样参数由服务端管理，避免工具参数膨胀及无边界计算。

| 阶段 | auto 解析结果 | 返回内容 |
| --- | --- | --- |
| SELECTING_HAND | play | 当前排列的出牌候选、持牌收益、有限排列建议 |
| SHOP、BLIND_SELECT、PACK | build | 可见选择与后续盲注的比较；PACK 使用真实包内选项 |
| MENU、ROUND_EVAL、GAME_OVER | 无适用分析 | `unavailable`，原因 `unsupported_phase` |

`draw` 只显式调用；初期不随 `auto` 自动运行。第一阶段只发布 `auto`、`play` 两个枚举值，后续模块通过验收后再扩展 schema，避免暴露不能工作的参数。SHOP 等阶段在第一阶段返回 `unavailable/module_not_implemented`。

工具标注：`readOnlyHint=true`、`destructiveHint=false`、`idempotentHint=true`、`openWorldHint=false`。同一输入和快照重复计算不改变游戏；工作预算不同可能导致完成度不同，幂等不意味着耗时和输出字节完全相同。

## 3. revision、观察基线和并发

`game_analyze` 必须使用调用方最近一次 `game_observe`、`game_start` 或 `game_action` 获得的 revision。结果中的 `rev` 只表示“本次分析基于哪份状态”，不颁发新的动作 revision。

处理顺序：

1. 在 `src/server.ts` 现有串行队列中处理请求，复用工具层的短 revision 还原规则；未颁发或非最新 revision 返回 `stale_state`。
2. 通过新的只读 RPC `sf.analysis_snapshot` 一次获取分析输入。参数包含完整 revision 和桥接实例标识，由 Lua 在稳定边界校验；变化则返回 `stale_state`，不自动刷新后继续分析。
3. 检查 ready、未解决操作、终局以及阶段。未就绪或操作未解决时返回 `unavailable`，不运行分析，也不解除任何动作锁。
4. 在不可变快照上计算；完成后通过同一只读入口的轻量 revision 检查模式复核。若阶段、实例或任何分析依赖发生变化，返回 `stale_state` 并丢弃候选。
5. 返回独立分析结果，不更新 `tools/index.ts` 的 `delivered` 或 `issued`，不合并进 observation v3 的 `state`。

`sf.analysis_snapshot` 参数约定为 `{instanceId, revision, mode:'snapshot'|'check'}`。snapshot 模式返回公开分析输入；check 模式只返回完整 revision 和稳定性状态，变化时统一报 stale_state。两种模式都必须从不触发计分的公共状态读取层构建指纹，不能转调当前可能运行影子计分的 `snapshot()`。公共指纹依赖的提取逻辑集中复用，避免普通观察和分析各用一套 revision 语义。

缓存命中也要做最终 revision 检查。`game_action` 仍按原流程重新校验 revision；分析期间的人类操作不能被串行 MCP 队列阻止。

**不能直接调用现有 `backend.observe()` 作为分析预读。** 当前该方法在部分情况下会检查完成操作并释放客户端的不确定状态锁；分析应有独立只读路径，确保“分析成功”不隐含恢复动作权限。

新增分析依赖必须参与桥接的公共 revision 指纹，且在所有观察／动作校验路径中一致使用。例如 Joker 当前可见成长值、回合内牌型记录、完整牌组组成变化不能只改变分析结果而不使旧 revision 失效。读取本身不增长 serial；相同状态重复读取返回相同 revision。

## 4. 返回契约

成功沿用 `{ok:true,value:{...}}`；传参错误、过期状态、桥接故障沿用现有错误 envelope，分析请求自身从不派发游戏动作，因此 `applied=false`。

```ts
type AnalyzeResult = {
  v: 1;
  rev: string;
  phase: string;
  focus: 'play' | 'draw' | 'build' | null;
  status: 'complete' | 'partial' | 'unavailable';
  reasons?: Issue[];
  play?: PlayAnalysis;
  draw?: DrawAnalysis;
  build?: BuildAnalysis;
  work: {
    evaluated: number;
    total?: number;
    stopped?: 'budget' | 'candidate_cap';
  };
};
type Issue = {code: string; subject?: string; message: string};
```

`complete` 表示完成约定搜索空间，不表示找到整个游戏的最优策略，也不表示每个候选都是确定分数。预先声明的 bounded 搜索全部完成可以为 complete；因预算或数量上限未完成原定搜索则为 `partial`，必须说明已计算数量和搜索范围。`unavailable` 表示没有可用模块或无法建立有效输入；原因不能藏在空数组中。

`work` 统计本 focus 的主要候选工作单元：play 是原排列的出牌选择，draw 是候选与补牌样本对，build 是变体与牌组样本对。排列、补牌或构筑子搜索各自另外报告完成度；不能用完成基础出牌枚举掩盖排列搜索中断。

结果自包含，无 delta 合并规则。文本使用英文，字段结构使用 TypeBox 校验。默认每个模块最多返回 `limit` 个主要候选，排列建议最多 2 个；公共快照和逐次触发日志不整份回显。

### 4.1 数字可信度

每个分数使用有判别字段的联合类型：

```ts
type Score =
  | {kind: 'exact'; value: string}
  | {kind: 'estimate'; value: string; basis: string; issues: Issue[]}
  | {kind: 'unavailable'; issues: Issue[]};
```

- `exact`：当前可见状态、该候选涉及的全部规则及其顺序均有验证覆盖，且没有影响数值的随机或未知分支。
- `estimate`：有明确近似方法，如受支持随机效果的期望或固定构筑采样。必须标明假设，不自动升级为保底分数。
- `unavailable`：存在无法有根据地近似的隐藏信息、未支持效果、历史或运行数值缺失。没有 `value` 字段。

大分数统一用十进制数值字符串表示，可带科学计数法；禁止 `NaN`、`Infinity`。内部数值运算应复现目标游戏的舍入位置和数值行为；不能通过使用 BigInt 或分数运算就声称与 Lua 一致。超过已验证数值范围时降级或拒绝数值，不输出伪精确位数。概率使用有限的 JSON number，范围 0..1。

`exact` 仍是事前计算，实际分数只由 `game_action.result` 确认。随机效果强制失败不普遍构成下界；缺失效果不默认为零；`E[XMult]` 也不能不经证明就直接代入复杂触发链作为总分期望。

### 4.2 简短示例

以下是独立的合成例子：当前有两张普通 2，Pair 基础为 10×2，没有其他效果，目标剩余 25。

```json
{
  "ok": true,
  "value": {
    "v": 1,
    "rev": "31",
    "phase": "SELECTING_HAND",
    "focus": "play",
    "status": "complete",
    "play": {
      "scope": "current_order",
      "candidates": [
        {
          "action": {"method": "play", "cards": [0, 1]},
          "family": "Pair",
          "score": {"kind": "exact", "value": "28"},
          "finishes": "yes",
          "facts": {"scoring": [0, 1], "heldBlue": [], "heldSteel": []}
        }
      ],
      "orders": []
    },
    "work": {"evaluated": 3, "total": 3}
  }
}
```

`finishes` 为 `yes|no|unknown`：只在 score 为 exact、当前目标和累计分数已知、候选可评分时给出 yes/no；估计值超过目标仍为 unknown。随机候选的达标概率另行描述，不混入该字段。

## 5. 公开分析快照

分析应读取结构化公开数值，不解析 `"0: Joker: +4 Mult"` 这类面向模型的字符串。新 RPC 返回 `AnalysisSnapshot`，独立于现有 `playerState()` 和紧凑投影，避免分析字段被白名单丢弃，也避免把全部中间数据塞进模型上下文。

最小数据包括：

| 数据 | 允许内容 | 缺失时处理 |
| --- | --- | --- |
| 版本和身份 | 完整 revision、runId、游戏版本、分析输入版本、规则兼容性 | 不能跨实例复用 |
| 稳定性和阶段 | phase、ready、outcome、未解决操作的公开状态及原因 | 阻塞时不运行评分或搜索 |
| 手牌 | 可见 rank/suit、增强、版本、蜡封、永久加成、debuff、forced、区域顺序 | 隐藏牌只保留允许的槽位状态 |
| Joker | 可见 key、顺序、版本、debuff、贴纸，以及逐规则白名单的公开当前数值 | 未知身份或依赖数值缺失，相关评分不可用 |
| 牌型和回合 | 已公开牌型基础值、等级、剩余手数／弃牌、当前累计分数、回合内已打牌型 | 不用全局 played 冒充本回合历史 |
| 盲注和规则 | 当前目标、公开 Boss 规则与动态限制、牌组／赌注／凭证 | 未知限制不当作无限制 |
| 资源和商品 | money、credit、容量、售价、购买价、目标限制、真实商店及包内选项 | 不猜测未来商品 |
| 牌组 | 无序聚合组成、数量、来源视图和不确定数量 | 不暴露抽牌顺序或实例映射 |

任何 Joker 的整个 `ability`、`G.GAME` 或随机状态表都不能直接传入。逐条定义“这个数值为何是玩家可知的”，缺失时保留 unknown，不能因为 Lua 可以读取就认为允许读取。隐藏 Joker 不得通过效果文本、缓存、排序建议或数值差异反向暴露身份。

现有 `game.cards()` 复现的是未打出牌预览，可能包括背面朝上的持牌。只有 `uncertainCards=0` 且组成数量等于 draw pile 数量时，才能把它当作精确的剩余抽牌组成；否则 draw 模块返回不可用，不能私下读取隐藏持牌并从总数中扣除。

build 还需要完整牌组组成；它与 remaining draw pile 是不同字段。必须通过原游戏允许查看的公开完整牌组视图取得，无顺序、无 card ID、无当前隐藏牌成员映射。若无法取得一致快照，第一阶段不估计整副牌的表现。

快照在同一 Lua 调用中收集，不跨 update、事件或动画边界。公共输入及其缺失标记参与一致的 revision 指纹；分析结果不参与指纹，避免计算自身导致 revision 改变。

## 6. 第一阶段：出牌与排列

### 6.1 当前排列的出牌

1. 枚举当前允许选择数量的所有子集，或检查调用方给出的 `plays`。
2. 静态过滤下标范围、强制牌、选择上限、剩余手数等限制。
3. 按原游戏牌型优先级识别牌型和评分牌；Boss 的评分禁止与“动作能不能派发”分开表达。例如某个选择能打出但被 Boss 判零分，不能标成工具参数非法。
4. 在当前手牌及 Joker 顺序下计算该次出牌，包括同次出牌内已支持的成长、重触发、持牌阶段和最终修正。
5. 提取与取舍有关的事实，返回少量有差异的候选。

8 张手牌最多有 218 个 1–5 张子集；10 张是 637 个。手牌变大时按预算截断，不能依赖固定“最多 8 张”的隐藏假设。

候选保留策略：先保留可确定结束盲注的选择和最高可比较分数，再保留不同牌型、蓝蜡封／钢铁持牌、避免成长重置、单张复制等有区别的选项。候选集中不把各种价值压成一个未经验证的总 utility。相同质量内可按分数排序；exact、不同假设的 estimate 和 unavailable 不强行混排成统一排行榜。

`facts` 使用短结构化字段，仅返回与当前构筑有关的内容：评分牌、非评分附带牌、持有蓝蜡封和钢铁、已支持的成长或重置效果。未知成长效果不能输出“安全”。指定 `plays` 模式保留每组的计算结果或拒绝原因，不偷偷替换成系统搜索出的更好选择。

### 6.2 排列建议

基准候选只针对当前顺序。更好排列放入独立 `orders`，每条包含：

- 一个当前可执行的完整 `rearrange` permutation；
- 当前最佳可比较分数和重排后的分数；
- 重排后用于评估的选择描述；
- `requiresFreshAnalysis=true`。

一次建议只调整一个区域；有收益的组合排列可以在执行并重新观察后继续分析。`bestAfter` 仅供比较，不能作为自动排队的下一动作；重排后所有下标都必须从新状态重新取得。

先搜索会改变触发结果的排列：首张评分牌、Photograph／Hanging Chad、Blueprint／Brainstorm 目标、加法和乘法 Joker 顺序。普通不敏感排列归并，完整 Joker 排列和手牌排列使用独立上限与预算。必须明确 `exhaustive` 或 `bounded`，不能把局部搜索说成全局最优。没有排列敏感效果时不运行排列搜索。

### 6.3 评分器选择

评分器使用统一内部接口：`score(snapshot, selection, order) -> ScoreResult`，返回数值质量、牌型、评分牌、必要事实和不支持项。搜索器不依赖某种计分实现。

**第一阶段建议使用 TypeScript 纯函数评分器，对已验证规则子集发布能力。** Lua 负责读取公开数值，Node 负责枚举和计算；不会在观察路径里临时移动真实 CardArea、调用结算函数、推进 RNG 或回滚全局表。这也为后续补牌、买牌和改牌的假设快照提供同一计算基础。

已有 `play/mod/scoring.lua` 通过替换全局、调用原游戏结算再恢复的方式算分，可作为另一种后端研究，但不能直接把它的文本行当作可信分析契约：它需要结构化覆盖报告、随机分支语义及独立的副作用验证。原生路径只适用当前手牌，也不能自然用于假想抽牌和商品变体。

若未来采用原生影子后端，必须先证明对游戏表、元表对象、事件队列、RNG、存档和外部 Mod 状态均无残留修改。前后公开快照相等只是必要检查，不能证明没有不可见副作用。该后端未通过此门槛前，不作为只读工具的生产计算路径；纯函数后端不得调用它补齐缺失规则。

现有原生计分是否继续随 `game_observe` 返回，是独立的实施选择；本提案不删除或改写当前工作区行为。新 `game_analyze` 不得通过调用带有影子计分的观察方法间接执行它。

## 7. 规则覆盖与原游戏一致性

支持清单以“规则 + 交互 + 动态输入 + 数值范围”为单位，不能仅用支持多少张 Joker 衡量。

建议的第一批覆盖顺序：

1. 普通牌型、基础 Chips/Mult、评分牌识别、当前顺序和强制选牌。
2. 确定性增强、版本、红蜡封、持有 Steel、基础 Chips／加法 Mult／XMult Joker。
3. Photograph、Hanging Chad、Mime、Baron 等确定性重触发链。
4. Blueprint、Brainstorm、牌型改变规则及其与上述效果的交互。
5. Boss 特殊限制、同次出牌成长、概率及更复杂的物品交互。

每个批次只在相关测试通过后声明支持。已经支持单张 Joker，不代表任意复制、重触发、成长和 Boss 组合都 exact。未支持的关键效果使完整数值 unavailable；可以返回不依赖该效果的事实，但不能删除它后继续比较“总分”。只有被证明对该候选无关的效果才允许忽略，并记录依据。

规则以当前目标游戏 1.0.1o 的实际结算行为为准。中文或英文描述用于解释，不作为数学规则的解析来源。对改变结算的第三方 Mod 使用明确兼容状态；无法确认时不得用原版规则输出 exact。共存的桥接 Mod 与真正改变结算的 Mod 应区分检测。

独立实现评分规则，不直接移植 `balatro-ai` 的 AGPL 源码到本项目的 MIT 代码中。若将来决定复用，先单独确定相应授权和分发方式；本设计不依赖该复用。

## 8. 第二阶段：有限补牌分析

draw 模块从精确公开剩余组成出发，比较少量弃牌选择及出牌后补牌选择。支持两种清楚区分的方法：

- 小状态可枚举时，使用组合计数给出一次抽牌完成某个牌型的精确概率。
- 状态较大时，使用本地固定伪随机采样，评估补牌后的一次最佳出牌。

候选优先来自牌型缺口、当前高分选择和重要持牌保留，不遍历完整弃牌策略树。建议默认每种动作最多 4 个候选、每候选 64 个样本；这是待测的初始预算。采样按公开规范化牌组排序，使用服务端常量，不使用游戏 RNG、游戏种子或真实 draw order；候选尽量共用抽样以降低比较噪声。

每条候选明确报告：当前即时分数、下一手分数统计、`finishProbability`、样本量、区间方法和资源消耗。出牌后再出一手需要剩余至少两手；弃牌后出一手需要剩余至少一次弃牌和一手。必须分别标注 `play_then_play` 与 `discard_then_play`，不能仅按达标概率跨资源消耗排序。

区间只表示采样误差，不覆盖规则模型误差。牌型完成概率也不等于达标概率；有限两步达标概率更不等于整局胜率。补牌后可能发生的成长、Boss 抽牌行为和状态变化没有覆盖时，拒绝该场景或明确降级，不能只替换手牌而冻结本应改变的数值。

当前已存在 exact 的立即结束选择时，默认停止补牌搜索并返回 `finish_available`，避免引导模型为了更高估计值浪费资源。

## 9. 第三阶段：商店、卡包与构筑

build 输出三个块，分别表达当前可见内容和假设：

- `baseline`：冻结当前构筑，对可见后续盲注估计输出分布和缺口；不能把抽到的最高分样本当稳定能力。
- `offers`：可见商品、Planet、可验证 Tarot 目标、有限 sell-then-buy 替换的前后比较，包含净花费、利息影响、槽位和贴纸约束。
- `horizon`：临时 Joker 到期后的构筑及下一 Ante 的普通目标情景，未知 Boss 不伪装成真实下一 Boss。

每个变体与 baseline 使用相同公开牌组样本，比较每手及有限回合输出、达标频率和花费。Eternal 不能作为替换对象；Rental 成本和 Perishable 剩余寿命明确进入分析。当前收益与“经过若干次改牌后”的引擎潜力分开返回；未来 fuel、未拥有搭档和未知商店供给必须标为 hypothetical，不能合并到可购买方案的收益中。

替换探索要报告搜索范围，例如最多比较 3 个可出售 Joker，不能只挑最低即时分数的一张就声称最佳替换。每个方案最多 2 个确定性步骤，执行成本和槽位按步骤验证；候选不因存在于 analysis 就获得后端合法性保证。

卡包购买只比较费用、种类和资源机会；未打开时不预测内容。打开后可比较真实选项和可见目标；未知抽取、随机创建、未来商店停止在分析边界。包内手牌不是打牌阶段，不能运行“现在出牌”的候选生成。

build 的 `clearChance` 必须附带有限策略说明：抽样方式、出牌／弃牌近似和冻结的成长效果。对不支持的 Boss 或完整牌组未知，仍可给出价格和利息等确定事实，但不返回数值过关概率。

## 10. 运行预算、缓存与取消

初始预算用于实施调优，不是已经测量的性能承诺：

| focus | 本地计算预算 | 补充限制 |
| --- | --- | --- |
| play | 250 ms | 基础选择先算；最多 512 次额外排列评分 |
| draw | 1 s | 最多 8 个动作候选，每个默认 64 个样本 |
| build | 2 s | 先完成 baseline，再比较至多 12 个可见变体 |

RPC 时间包含在现有整体 deadline 内，本地预算不得超过剩余时间。候选计算必须可中断；建议用单个 Node worker 执行纯函数计算，或实现有明确让出点的分块循环。不能让一次长同步循环阻塞取消处理和工具队列。没有完成一个有效候选时返回 unavailable；完成部分候选后预算用尽返回 partial。调用方主动取消或整体超时仍使用 cancelled／timeout 错误，不伪装成完整结果。

缓存使用规范化公开输入、桥接实例／runId、完整 revision、规则版本、参数和预算配置作为键；可直接用规范 JSON 文本，不需要内容哈希。保持每连接有上限的内存 LRU，不落盘。规则版本、实例、牌局或任何依赖改变后失效；不可用结果不能无限期缓存。

默认模型输出目标为 play 不超过约 4 KB、draw/build 不超过约 8 KB；需实际测量后调节候选数。预算中断原因、未支持效果和概率假设不能为了字节目标删掉。逐次触发明细和采样内部统计只进入经过公开信息白名单检查的 trace。

## 11. 模块与接入点

沿用当前顶层目录，避免新顶层目录遗漏构建和发布：

```text
env/analysis/contract.ts        # 输入、快照、结果 schema 和质量联合类型
env/analysis/normalize.ts       # 公开输入规范化、依赖完整性检查
env/analysis/rules/             # 纯规则、覆盖清单、交互检查
env/analysis/scoring.ts         # 单次出牌评分接口
env/analysis/play.ts            # 子集和排列搜索
env/analysis/draw.ts            # 一次补牌分析，第二阶段
env/analysis/build.ts           # 构筑与可见变体，第三阶段
env/analysis/worker.ts          # 预算、取消、计算任务
tools/analyze.ts                # 独立工具注册、短结果和 trace
play/mod/analysis.lua           # 只读公开数值白名单和快照
```

现有文件的预期改动：

- `env/contract.ts`：增加可选 `analyzeSnapshot` 后端能力及其输入类型，普通观察 contract 不混入分析数据。
- `play/client.ts`：能力协商、严格快照校验、只读 RPC；不复用 act，不解除 uncertain 状态。
- `play/mod/bridge.lua`：`sf.analysis_snapshot`、公共依赖指纹与 revision 校验；`sf.health` 增加输入版本能力，例如 `analysis_snapshot_v1`。
- `play/mod/balatro_mcp_mod.lua`：加载公开快照模块，不在 love.update 中运行 Node 搜索。
- `tools/index.ts`／`src/server.ts`：共享 revision 校验和串行队列，独立注册分析工具；分析结果不经过会更新 delivered 的观察返回路径。
- `tools/guide.ts`、`skills/core.md`、`src/context.ts`：说明何时调用、数值质量和重排后重新分析；维持简短 bootstrap。

旧 Mod 缺少能力时返回 `unavailable/upgrade_required`，保留现有观察和动作功能；输入版本或游戏版本真正不兼容时返回 `incompatible_backend`。分析能力发布与部署验收分开记录，离线通过不能宣称运行中的 Mod 已加载。

## 12. 验证与上线门槛

第一阶段必须覆盖以下实质性检查：

1. **协议**：短 revision、跨连接／重启、内部读不更新 delta 基线；分析失败后下一次动作观察仍可正常恢复。
2. **公开信息**：种子、draw order、隐藏身份不进入输入、缓存键、数值结果或 trace；不确定预览组成不能用于精确抽牌分布。
3. **只读性**：分析不调用动作或 UI handler、不消耗 RNG、不建立事件、不改变锁和操作状态；未知 scorer 故障可恢复且不影响普通工具。
4. **原游戏差分**：在独立测试夹具中从同一公开局面计算，再实际执行该手并对比牌型、评分牌、关键阶段和最终分数。覆盖持牌、重触发、复制、Boss、成长和目标数值范围。实际动作只在测试明确授权的环境运行，生产分析路径不执行探测动作。
5. **搜索与索引**：强制牌、附带牌、较大手牌、预算中断、重排后的索引映射；返回的 action 与当前 snapshot 的区域顺序一致。
6. **降级**：随机效果、未知 Joker、动态数值缺失、第三方结算修改、非有限数值及部分覆盖交互；缺失不静默当零，估计不冒充必胜。
7. **资源**：取消响应、worker 终止、缓存上限、工具队列延迟和实际返回字节数。

评分预期必须来自独立规则推导或真实游戏执行记录，不能仅让测试调用同一评分函数生成期望值。副作用检查使用字段和事件／RNG 状态的结构比较，不使用 SHA256 测试。

上线顺序：先隐藏开发能力验证公开快照和评分内核，再发布 play，随后发布 draw，最后发布 build。每步在 `docs/validation.md` 记录执行过的检查、规则覆盖和是否实际重启验证，不把后续模块留空却宣传为完整能力。

要证明它让模型更会玩，另做同模型、同推理配置、同公开种子面板、同工具／时间预算的配对对照。记录 Ante 8 胜率、失败盲注、达标手数、动作错误、耗时和调用成本，并报告不确定性。协议正确、算分准确和整局策略收益是三个不同的验收结果。

## 13. 建议的第一阶段交付范围

第一阶段交付一个真实可用的 `game_analyze`：必填 revision，自动／指定出牌分析，最多 5 个默认候选，最多 2 个排列建议；结构化公开快照，纯函数评分子集，逐候选质量标记，预算与取消、独立 trace，以及不会改变观察基线的 MCP 接入。

第一阶段不承诺覆盖全部 Joker，也不返回补牌胜率或商店购买排名。缺失规则必须可见，且不能影响原有玩法接口。该范围先解决“模型反复心算、漏掉更好出牌或排列”的问题，并给后续补牌与构筑分析留下同一套可靠输入和评分基础。
